# 开发进度与验收入口

本页提供文档职责、状态规则和工作流程，不承载开发或修改日志。

- 当前任务、负责人及下一步：[任务台账](TASKS.md)。
- 阶段门及MVP实际结果：[验收清单](CHECKLISTS.md)。
- 开发过程、修改原因及会话接续：[开发日志](DEVLOG.md)。
- 重要调查、阶段验收、发行核验及精选证据：[报告索引与留存规则](reports/README.md)。

## 1. 四个固定入口

| 文件 | 用途 | 更新时机 |
|---|---|---|
| [TASKS.md](TASKS.md) | P0—P5 任务、工作包、状态、依赖、负责人、下一步、证据的唯一台账 | 开始/暂停/完成一项任务时 |
| [CHECKLISTS.md](CHECKLISTS.md) | G0—G5 阶段清单和 MVP-01—16 实际验收结果 | 运行验收、发生回归或切换阶段时 |
| [DEVLOG.md](DEVLOG.md) | 每次开发的变更、验证、阻塞和下一任务，便于跨会话接续 | 每项开发或独立改动完成后、继续下一项前；验证产生新结果后再次更新 |
| [reports/README.md](reports/README.md) | 重要报告索引与精选证据的留存约定 | 重要调查、阶段验收或发行核验时 |

根目录可执行 `pwsh -NoProfile -File scripts/check_progress.ps1` 查看阶段计数和检查一致性；它不改变状态，也不替代构建、测试、平台或性能验证。没有 CI 前本地执行；接入 CI 后使用同一命令。GitHub Issues/Projects 可以作为导航镜像，暂不建立第二份手动维护的进度权威，也不自动创建远端事项。

## 2. 状态和完成定义

任务状态固定为 Todo → Doing → Review → Done，也可从 Doing/Review 进入 Blocked；失败修复后回到 Doing。Todo 是未开始，Review 是代码/产物已具备但尚待完成必要核对，Done 是该子任务已有可核验的证据。Blocked 必须写明具体原因、解除条件和可继续的下一项。尚未开始但在等待前置的任务仍为 Todo，不把整个待办列表都标成阻塞。

- 开始 Doing：填写负责人，核对前置任务；同一执行者通常同时只做一个 Doing，优先结束一条可运行链路。平台/内核探索可作为 P0 单独交付，不绕过产品集成依赖。
- 进入 Review：链接具体 DEVLOG 标题条目、不可变 Actions 运行或已有专项报告，简记实现版本/位置、验证命令与真实结果及限制；日常改动不生成 report，不把历史输出另写成 Markdown。确有长期价值的重要调查才按需使用[专项摘要模板](templates/task-report.md)。
- 标记 Done：本任务范围已实现，所需检查通过且无未处理阻断缺陷；证据结论与设计/任务/验收追踪同步。阶段门/MVP 仍用逐项结论报告，可引用不可变 CI 运行及精选证据。提交前可记录准确工作区/构建标识，不为记进度自动提交代码。
- 修复回归：相关任务退回 Doing/Review，受影响的验收结果及相关阶段标为 Stale；保留重要失败原因、适用版本和后续结果，不要求永久保存每次原始输出。

依赖重新打开时，不要求把所有曾完成的后续实现任务全部退回 Todo；它们可保留有证据的 Done 历史，但相关运行结论必须 Stale。检查脚本约束正在进行的 Doing/Review 前置状态，阶段 Pass 则要求该阶段全部任务当前 Done；不会因历史依赖退回就强制开发者重写不受影响的功能。

验收状态固定为NotRun / Pass / Fail / Blocked / Stale。NotRun表示未运行或修订范围尚未完成逐条件证据核对；Blocked表示缺环境/前置，不能当失败或通过；Stale表示过去通过但行为/版本变化使证据失效。按设计19/1.9的16项G2本机条件全部必需，没有N/A；日常环境/宿主扩展单独归P3-14。范围收窄不自动产生Pass，同版本有效证据核对后可复用，不能因未做被移除的全矩阵继续加码。

只统计“任务 Done 数”“已通过验收数”和“当前门的状态”，不把任务项等权换算成产品完成百分比。P2 子项 Done 不表示整个 W18 更新/打包工作包已完成；P3—P5 粗任务进入实施前再拆细，并保持工作包与需求映射。需求减少/验收跳过必须先修改设计及追踪，不能只删清单。

## 3. 每次开发的检查清单

仅在受影响字段更新当前状态、负责人、证据和待办；常规过程、验证命令与结果写入[开发日志](DEVLOG.md)，重要调查/阶段结论写报告。原始日志、批量截图和采样输出写 Git 忽略的 build/ 或 CI artifacts（默认14天）；需要长期复核的少量证据人工精选到 reports/evidence/。

逐项同步是执行顺序要求：每完成一项独立改动，先更新受影响的文档/台账/DEVLOG，有相关专项报告时更新其结论，再继续下一项。实现已具备但验证尚未完成，记录“验证中/NotRun”；新结果产生后再次更新。共同完成一个修复的多文件视为一项，不要求逐文件记录或改动全部文档，详见[开发规范](../development/cpp_style.md#4-逐项开发与文档同步)。

以下是每次使用的操作清单，不在这里累计勾选；日常结果简记到台账和开发日志。

开始前：

- [ ] 读 TASKS、CHECKLISTS 和 DEVLOG 的最新记录，选一个前置已满足的任务，读取对应设计章节。
- [ ] 查看工作区已有修改，保留其他任务成果；确认本次交付边界和明确的完成条件。
- [ ] 更新负责人、Doing 和下一步；缺工具/环境写具体 Blocked 原因，继续独立可做事项。

交付前：

- [ ] 记录实现位置/版本；确认成功、空/错、取消/迟到响应及恢复中适用于本任务的行为。
- [ ] 代码交付做一次 Windows 增量构建和受影响的功能/测试；文档修改只运行文档检查，低风险视觉修改不新增镜像测试，不重复无影响的完整矩阵。
- [ ] 资源敏感改动选一个实际场景做10—30秒单轮短测；已有证据未受影响则复用。记录三项内存指标、同环境基线变化与有界生命周期，不设固定MB门槛；短测不代表长期/CPU/帧通过。
- [ ] 在 DEVLOG 或相关报告列出未覆盖范围/遗留问题；更新受影响的 Review/Done 与验收，对变化影响的旧 Pass 标 Stale。
- [ ] 写 DEVLOG 的可接续下一任务；更改设计时重建合并版，再运行进度检查和 `git diff --check`。

## 4. 接续入口

- 按[任务台账](TASKS.md)选择依赖已满足的任务，按[验收清单](CHECKLISTS.md)确认待补证据；不从历史报告标题推断当前状态。
- 内存优化各切片的历史Review/NotRun与未关闭风险见[验证范围](reports/20261026_client_memory_optimization.md#验证范围)。后续真实构建结果单独引用，静态检查和旧包不能证明当前源码已通过全部验收。
- 读取[开发日志](DEVLOG.md)接续具体上下文；设计边界见[设计入口](../design/README.md)，构建和部署规范见[构建基线](../baseline/build_and_package.md)。

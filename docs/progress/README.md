# 开发进度与验收入口

日常以 [TASKS.md](TASKS.md) 为当前状态入口：进行中、未来开发计划、未关闭风险及近期结果。原 P0—P5 未完成事项保留原 ID 和历史证据链接；新增需求按需加入计划，不强制编号。按需查看 [DEVLOG.md](DEVLOG.md) 的复杂过程与接续信息，以及 [CHECKLISTS.md](CHECKLISTS.md) 的发布清单和历史能力证据。重要调查和不可替代的证据见 [报告索引](reports/README.md)。

## 文档职责与规格维护

| 内容 | 权威来源 | 其他位置的写法 |
|---|---|---|
| 功能行为、接口、失败与恢复语义 | 对应 [设计分册](../design/README.md)；跨模块接口见03 | 摘要引用所属章节；调整行为时先明确预期与验收，再实现并同步受影响的引用 |
| 设计取舍与替代关系 | [16 设计决策](../design/16-设计决策风险与需求追踪.md) | ADR引用功能契约，已替代决策明确标识，避免作为另一份现行规格 |
| 编码、命名、所有权和工具约束 | [源码规范](../development/cpp_style.md) | AGENTS保留关键约束与入口 |
| 日常范围、状态与交付记录 | 本文件 | 其他规范引用本文件，命令参数见 [构建说明](../baseline/build_and_package.md#日常定向验证) |
| 当前任务、风险与下一步 | [TASKS](TASKS.md) | 历史结果和复杂过程保留链接，不在多处维护当前状态 |
| 发布候选核验 | [CHECKLISTS](CHECKLISTS.md) | 按候选版本和声明范围记录，自动打包成功不代替功能验收 |
| 原始输出与长期证据 | [报告留存规则](reports/README.md#留存规则) | DEVLOG和任务只保留结论、必要上下文与证据链接 |

普通任务只需在现有条目或工作说明中写清预期行为、受影响契约和选定检查；已有契约足够时直接引用。改变行为先修订对应规格，再完成实现与验证，发现偏差及时回到同一契约修正。关键数据、权限和恢复验收从 [16的验证入口](../design/16-设计决策风险与需求追踪.md#31-关键验收的验证入口)选择；入口用于定位检查，不表示已经通过，也不要求为每个小改动新建规格、报告或追踪编号。

## 状态与记录

- 任务使用“待做 / 进行中 / 完成 / 阻塞”；单人工作不要求负责人或编号，真实前置依赖仍须满足。实现完成但必要验证未完成，保持“进行中”并说明未验证内容。
- “完成”仅表示所述范围的必要验证已完成，不代表整个产品或其他平台通过。测试实际结果按需写明 Pass、Fail、NotRun、Blocked 或 Stale；不能把未运行、失效或失败写成通过。
- 普通桌面任务按改动和风险选择可执行的构建及针对性验证；物理触摸、真实读屏、其他平台或长时压力等专项不自动成为日常任务的完成条件。设备或环境不可用时注明未验证范围，按已测范围完成；与本次目标直接相关的实际故障仍须处理，失败的探针和未关闭风险不得改记为通过。发布时再按实际声明的支持范围决定所需专项验收。
- 一次交付或会话结束时更新受影响的 TASKS 当前状态、结果和下一步。简单改动在一处写清即可；重要失败、复杂验证、交接或恢复上下文按需记 DEVLOG。若中途暂停，记录足以接续的信息。
- 功能行为或使用方式变化时同步对应设计/使用说明；发布核验结果变更时更新 CHECKLISTS。日常不强制每个改动同时修改多个文件，也不强制报告、工作包或远端事项。
- 旧证据按版本和范围使用；变更影响结论时，明确失效范围或标记 Stale。保留重要失败和未关闭问题，不必把每次重试或历史截图逐条复制到台账。
- “未来开发计划”只保留未完成工作；完成项移至“近期完成”，保留原编号、验证范围和必要证据。剩余待验或未关闭风险单列，不让已完成条目长期占据计划区。
- TASKS保留少量近期结果和下一步，详细过程引用已有记录。完成记录妨碍检索时按批归档，通常保留最近5—10项摘要即可；归档不是每次交付的固定动作。归档前将仍为待做/进行中/阻塞的条目、未关闭缺陷和验证缺口留在当前入口，原记录及重要失败按原版本保留并修复引用。

## 最小交付记录

一次交付在 TASKS 简记以下内容，可写成一个段落：

```text
改动与交付范围：
已运行的构建 / 定向测试或人工检查及结果：
未关闭问题 / 未验证的相关范围与下一步：
```

同一修复涉及多个文件时合为一项。环境和既有风险引用已有记录；复杂经过才使用 DEVLOG，重要调查或发行核验才使用报告。记录结果所适用的范围，未运行的产品测试保持 NotRun。

## 按风险选择验证

| 范围 | 交付前验证 |
|---|---|
| 纯文档 | 相关文档与链接检查；不构建产品 |
| 局部样式、间距和悬停 | Windows 增量构建及受影响页面的定向检查；自动检查与人工检查择能覆盖风险者，不叠加完整 UI 矩阵 |
| 普通业务逻辑、模型和界面交互 | Windows 增量构建；受影响的现有测试或针对性人工检查，说明范围 |
| 配置、订阅和持久化 | 增加成功路径、错误/中断时保留旧数据的定向验证 |
| 系统代理、TUN、权限和更新 | 增加适用的真实或隔离环境恢复、退出和失败路径；缺权限或环境如实记录 |
| 资源敏感改动 | 有理由时做可比较的代表场景短测，已有有效证据可复用；长时、压力和图形专项按风险扩展 |
| 对外发布 | 按 [发布清单](CHECKLISTS.md) 核对当前版本与实际声明的支持范围 |

## 日常范围与停止规则

1. 开始前选定本次影响范围和必要检查，普通任务用一句话或工作计划说明即可，不另写验证方案。默认执行一次增量构建和最小的一组定向验证；有足够覆盖后结束，不为增加测试数量继续扩展。
2. `scripts/build_windows.ps1` 默认只构建产品及 `contracts`、`qml_smoke` 冒烟所需目标；headless 默认仅 `contracts`。用 `-Test` 指定受影响的 CTest 名称，只补建对应测试程序；用 `-BuildOnly` 配合针对性人工检查，测试结果记 NotRun。生产 `-Release` 使用 `BUILD_TESTING=OFF`，不编译或运行测试。默认冒烟不能替代与本次改动直接相关的必要验证。QML 改动增加 `-Lint`；`-Fast` 和 `-Full` 自动执行 QML lint。自动发布仅依赖生产构建、打包校验和随包启动冒烟，回归测试工作流只按需手动触发。命令示例见[构建说明](../baseline/build_and_package.md#日常定向验证)。
3. 局部 UI 只检查受影响页面或控件；文本/翻译与文字布局变化补受影响的语言，主题色变化补明暗主题，响应式布局变化补相关窄窗/大字号，键盘或可访问性语义变化补相关交互。共享组件选择有差异的代表使用点。仅原生行为、渲染或平台问题需要时补原生检查，不默认全页、双语、主题、字号与离屏/原生交叉组合；无需为纯样式新增镜像测试。
4. 无代码或环境变化的偶发失败，最多先定向复跑一次并保留首轮结果；再次失败或结果不一致，转为有明确假设的诊断，不循环整套回归或追求连续 N 次通过。竞态、时序与稳定性修复可按复现概率和问题目标安排有界重复。与本次改动相关的实际故障须处理；无关既有问题集中记录或引用，不自动扩大当前任务。
5. 完整回归用于发布候选、工具链/依赖升级、广泛公共机制变化或有证据的跨模块回归，记录触发原因；本地显式使用 `-Full`，远端按需手动运行 `validation`，当前仅执行 Windows，其他平台就绪后加入同一工作流。`-Fast` 保留原快速范围供本地跨模块检查，覆盖核心行为和可访问性语义；焦点几何、视觉、合成触摸及长生命周期检查按改动定向或完整运行，具体名称见[构建说明](../baseline/build_and_package.md#日常定向验证)。只改一个配置/订阅/权限模块时，先跑相关成功与关键失败/恢复路径，不因模块风险高就默认跑所有不相关测试。未修改的有效证据可复用。
6. 资源敏感改动默认一个代表场景、单轮 10—30 秒同环境短测；仅在噪声妨碍结论、明显回归或持续增长时重复/延长。普通 UI 修改不附带性能测试，长时、压力、GPU、读屏、物理触摸及其他平台按专项或发布声明开展。
7. 检查结束后按[最小交付记录](#最小交付记录)更新受影响任务；设计和使用说明同步实际行为变化，发布结果按候选版本维护。

历史 G0—G5 和 MVP-01—16 保留为各自范围的验证基线；不要求前一门通过才能陈述独立能力的真实验证结果，也不能凭历史证据宣称当前版本或未测平台通过。宣称完整历史 G2 范围时仍须满足其原本 16 项条件；发布则核对当前声明能力和未关闭风险。

原始日志、JUnit/CSV、批量截图和临时夹具按[留存规则](reports/README.md#留存规则)存放；禁止真实订阅、节点凭据及其他秘密入库。

根目录运行 `pwsh -NoProfile -File scripts/check_progress.ps1` 检查本地 Markdown 链接和显式任务状态；它不修改台账，不替代构建、测试或发布核验。源码布局及设计生成检查按仓库约定执行。

## 2. 状态和完成定义

任务状态固定为 Todo → Doing → Review → Done，也可从 Doing/Review 进入 Blocked；失败修复后回到 Doing。Todo 是未开始，Review 是代码/产物已具备但尚待完成必要核对，Done 是该子任务已有可核验的证据。Blocked 必须写明具体原因、解除条件和可继续的下一项。尚未开始但在等待前置的任务仍为 Todo，不把整个待办列表都标成阻塞。

- 开始 Doing：填写负责人，核对前置任务；同一执行者通常同时只做一个 Doing，优先结束一条可运行链路。平台/内核探索可作为 P0 单独交付，不绕过产品集成依赖。
- 进入 Review：链接已保存的 [任务报告模板](templates/task-report.md) 实例，包含真实代码/产物位置、build ID/commit 或工作区补丁说明、验证命令与结果、失败/取消/恢复、资源影响及限制。源码/文档任务可注明相关运行检查不适用并解释；不能用纯模板充当报告。
- 标记 Done：本任务范围已实现，所需检查通过；报告结论明确、无未处理阻断缺陷；设计/任务/验收追踪同步。可以由执行者完成自检，阶段验收仍须独立记录。任务在提交前完成可写准确工作区/构建标识，提交后补 commit，不为记录进度自动提交代码。
- 修复回归：相关任务退回 Doing/Review，受影响的验收结果标为 Stale；已通过的相关阶段一并 Stale。新报告保留旧运行记录，不覆盖失败历史。

依赖重新打开时，不要求把所有曾完成的后续实现任务全部退回 Todo；它们可保留有报告的 Done 历史，但相关运行结论必须 Stale。检查脚本约束正在进行的 Doing/Review 前置状态，阶段 Pass 则要求该阶段全部任务当前 Done；不会因历史依赖退回就强制开发者重写不受影响的功能。

验收状态固定为 NotRun / Pass / Fail / Blocked / Stale。NotRun 表示未运行；Blocked 表示缺环境/前置，不能当作失败或通过；Stale 表示过去通过但当前代码/内核/配置已变化，需要重跑。MVP 16 项全部必需，没有 N/A。检查项勾选表示已有报告中的事实证据，不能因为代码看起来齐全就勾选。

只统计“任务 Done 数”“已通过验收数”和“当前门的状态”，不把任务项等权换算成产品完成百分比。P2 子项 Done 不表示整个 W18 更新/打包工作包已完成；P3—P5 粗任务进入实施前再拆细，并保持工作包与需求映射。需求减少/验收跳过必须先修改设计及追踪，不能只删清单。

## 3. 每次开发的检查清单

逐项同步是执行顺序要求：每完成一项开发任务或独立改动，先更新受影响文档及台账/报告/DEVLOG，再继续下一项，不等会话结束集中补写。实现已具备但验证尚未完成，记录“验证中/NotRun”；新测试或修复结果产生后再次更新。共同完成一个修复的多文件视为一项，不要求逐文件流水记录，详见[开发规范](../development/cpp_style.md#4-逐项开发与文档同步)。

以下是每次使用的操作清单，不在这里累计勾选；结果写到台账、报告和开发日志。

开始前：

- [ ] 读 TASKS、CHECKLISTS 和 DEVLOG 的最新记录，选一个前置已满足的任务，读取对应设计章节。
- [ ] 查看工作区已有修改，保留其他任务成果；确认本次交付边界和明确的完成条件。
- [ ] 更新负责人、Doing 和下一步；缺工具/环境写具体 Blocked 原因，继续独立可做事项。

交付前：

- [ ] 记录实现位置/版本；确认成功、空/错、取消/迟到响应及恢复中适用于本任务的行为。
- [ ] 代码交付做一次 Windows 增量构建和受影响的功能/测试；文档修改只运行文档检查，低风险视觉修改不新增镜像测试，不重复无影响的完整矩阵。
- [ ] 资源敏感改动选一个实际场景做10—30秒单轮短测；已有证据未受影响则复用。100 MB只检查专用工作集，短测不代表长期/CPU/帧通过。
- [ ] 报告列出未覆盖范围/遗留问题；更新 Review/Done 与相关验收，对变化影响的旧 Pass 标 Stale。
- [ ] 写 DEVLOG 的可接续下一任务；更改设计时重建合并版，再运行进度检查和 `git diff --check`。
